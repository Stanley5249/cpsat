# Design

Rust owns the model. Protobuf defines the contract. C++ executes the solver. The
FFI exposes only capabilities that Rust cannot implement directly.

The goal is the functional capabilities of the official Python CP-SAT binding,
through an idiomatic Rust API that writes into the Protobuf model. `cargo build`
acquires OR-Tools and builds the bridge, with no manual OR-Tools, Conda, or
Python install, and normal builds regenerate neither Protobuf code nor OR-Tools.
A persistent incremental solver, OR-Tools subsystems outside CP-SAT, custom
propagation, and a CP-SAT-only fork are out of scope.

## Architecture

```text
user code
   |
crates/cpsat          CpModel, Buffa types, CpSolver, StopHandle, diagnostics
   |  (safe Rust, owns the model)
crates/cpsat-sys      build.rs, raw extern "C" declarations, links = "ortools"
   |  (serialized bytes, fn pointer + context, opaque session)
cpsat-sys/bridge      extern "C" over SolveWrapper and CpSatHelper
   |
ortools.dll / libortools.so  (SolveCpModel)
```

Rust owns the model, serialization, every model change, callback handling, and
error interpretation. C++ owns solver execution, the active solve and its stop
mechanism, and OR-Tools diagnostics. A bridge session lives for one solve and
never holds a second copy of the model.

`crates/cpsat/src` modules depend one way, and every module may use `proto` and
`error`:

```text
expr/        handles, LinearExpr, FloatExpr, Domain        uses nothing else
constraint/  Constraint, ConstraintIndex, comparisons      uses expr
model/       CpModel: variables, intervals, lookups        uses expr, constraint
solver/      CpSolver, events, stops, responses, ffi       uses expr
proto/       generated by Buffa
```

## Facts verified against v9.15

Recheck these when the pinned OR-Tools version changes.

- The prebuilt `ortools` library already contains `SolveWrapper` and
  `CpSatHelper` from `swig_helper.h`, the native core of Python's solver.
- The C API in `cp_solver_c.h` has no callbacks and aborts on a parse failure,
  so the bridge wraps `SolveWrapper` instead.
- Solution and best-bound callbacks run under the response mutex, but log and
  solution events can come from different threads, so the bridge serializes
  them.
- Python's `ExtSolveWrapper` stores the first callback exception, calls
  `StopSearch()`, and rethrows after `Solve` returns.
- Both prebuilt archives are dynamic, and `ortools.dll` loads HiGHS and SCIP
  even for CP-SAT.
- `cp_model.proto` is proto3 and `sat_parameters.proto` is proto2.

## Terms

Names follow the
[Rust API Guidelines](https://rust-lang.github.io/api-guidelines/naming.html)
and the C convention `prefix_object_verb`.

- **OR-Tools**: the upstream C++ library and its files.
- **bridge**: our C++ code and its C ABI in `crates/cpsat-sys/bridge/`, with
  functions named `cpsat_<object>_<operation>` after the Rust method, such as
  `cpsat_model_stats`.
- **FFI**: the Rust side of the C ABI, in `cpsat-sys` and `cpsat`'s private
  `ffi` module.
- **session**: the bridge object that serves one solve.
- **mode**: how the build acquires OR-Tools, the `download-libortools` or
  `build-libortools` feature, or `ORTOOLS_ROOT`.
- **wrapper**: a hand-written type that owns a Protobuf message, such as
  `CpModel`.
- **handle**: `IntVar`, `BoolVar`, `IntervalVar`, or `ConstraintIndex`.
- **literal**: a `BoolVar`, negated or not.

## Rules

Every change follows these rules.

- **Protobuf types.** Wrap a message only where its encoding is weakly typed:
  indices, `-i - 1` literals, flat interval lists, and `oneof` constraints. Use
  typed records such as `SatParameters` and `CpSolverResponse` as generated, and
  add methods to them.
- **Literals.** The schema refers to a row of `CpModelProto::variables` by its
  `i32` index. A field named `literal` reads that index as a Boolean on a 0-1
  variable, and the negative value `-i - 1` is the negation of row `i`, so a
  negation adds no row. `IntVar` holds a row index, which is never negative, and
  `BoolVar` holds a literal, which `!` negates as bitwise not. A literal enters
  a variable field only through `BoolVar::variable`, which drops the negation,
  or `LinearExpr::from`, which reads `!b` as `1 - b`. A method that edits a row,
  such as a domain change, takes `IntVar`. A method that sets a literal's truth
  value, such as `add_hint`, takes `BoolVar` and flips the value for a negation.
- **Paths.** Every public item has one path. `prelude` holds every hand-written
  item except `Error` and `Result`, which stay at the root. `proto` holds the
  generated types and `buffa` re-exports their runtime. Other modules are
  private.
- **Names.** Use Python's name wherever a Rust convention allows it, such as
  `constant` and `parameters`. Constructors drop `new_`, constraint constructors
  drop `add_`, and integer is the unmarked kind. The model and solver take
  Python's class names, `CpModel` and `CpSolver`. `CpModel::new_var` and
  `new_constant` keep the prefix, because they append to the model and a bare
  `var` reads like a getter. A value before insertion is a plain noun, such as
  `Constraint` and `Interval`. A handle takes the OR-Tools name where one
  exists, such as `IntVar` and `IntervalVar`, and is otherwise the noun plus
  `Index`, such as `ConstraintIndex`, because it is a row index and borrows
  nothing.
- **Entry points.** One method per meaning. Several input types share one method
  over a sealed trait, such as `value` over `Evaluate`, `new_var` over `NewVar`,
  `new_constant` over `NewConstant`, and `add_hint` over `Hint`. Take
  `impl IntoIterator` instead of a single-item twin.
- **Insertion.** `CpModel::new_var` appends what other parts of the model refer
  to, a variable or an interval, and returns the handle they take as input.
  `CpModel::add` appends a constraint that nothing refers to, and its
  `ConstraintIndex` only reads or edits that row.
- **Methods.** Operations on a model or response are methods on `CpModel`,
  `CpModelProto`, and `CpSolverResponse`, and `CpModel` forwards `solve`,
  `validate`, and `stats` to its message. Only `default_parameters` is a free
  function. Method names do not repeat the receiver.
- **Allocation.** Reads, predicates, and lookups allocate nothing, because
  callbacks and model-building loops call them often. Building owned model data
  and encoding each solve are the exceptions.
- **Ownership.** Take stored data by value through `impl Into<T>`, and borrow
  read-only data, such as `CpSolver::new(&SatParameters)`.
- **Failure.** A caller's programming error, such as `i64` overflow or a ragged
  table row, panics with a `# Panics` section. A failure the caller can cause in
  OR-Tools returns `Error`. `validate` returns `Error::InvalidModel`, while
  `solve` reports the `MODEL_INVALID` status. Types rule out structural
  mistakes, such as a negated literal where the schema wants a variable or an
  unbounded variable domain. The validator checks what depends on the model's
  current state, such as a variable's domain or an earlier hint. Check eagerly
  only what the validator cannot see.
- **Matched lists.** Items that belong together form one tuple, such as the
  `(interval, demand)` pairs of `cumulative`, so their lists cannot differ in
  length. Lists whose lengths must match but whose items do not pair, such as
  the two permutations of `inverse`, stay separate, and the validator reports a
  mismatch. Only an encoding that hides the mistake panics, such as table rows
  flattened into one list, which the validator would read as other rows.
- **Lookup.** A raw schema index returns `Option`. Indexing with a handle panics
  when the model lacks it, like a slice.
- **Builders.** A value configured before insertion takes `self` and returns
  `Self` with `#[must_use]`, such as `Constraint::only_enforce_if`. Change a
  constraint after insertion through `model[constraint]`. Variables and
  intervals change only through `proto_mut`, because a changed domain or
  interval body can break the handles that rely on it.
- **`#[must_use]`.** Every public method without side effects carries it.
  Appending model methods such as `new_var` do not.
- **Docs and tests.** `docs/conventions.md` sets the rules for doc comments,
  examples, and tests.
- **Visibility.** `pub` or private, except `pub(crate)` on handle indices,
  expression terms and evaluation, and `EventSet::bits`, which sibling modules
  share.

## Decisions

- **Crates.** `cpsat-sys` and `cpsat`, because `links` allows one native link
  per graph.
- **Codegen.** `just gen-proto` runs `buf generate` with the remote Buffa
  plugin, and the output is committed, so normal builds need no `protoc`.
- **Bridge build.** The `cc` crate with definitions read from
  `ortoolsTargets.cmake`, so the download mode needs no CMake.
- **Download.** The system `curl` and `tar`, which bring the system proxy and CA
  store. `build/fetch.rs` says when to switch to `ureq`.
- **Cache.** Archives, extractions, and source builds live in `CPSAT_CACHE_DIR`,
  each filled once under a `File::lock`, which sets the MSRV.
- **Runtime libraries.** Hard-linked or copied into `OUT_DIR/runtime` with their
  license notices. The `cpsat-sys` build script explains why.
- **Errors.** A `thiserror` enum in `cpsat`, `anyhow` in the build script.
- **README links.** Absolute URLs on `main` for `docs/`, because crates.io
  resolves relative links against each crate's directory. The license links stay
  relative, because each crate holds its own copies.
- **Solver.** `CpModel::solve` for the plain case, and a `CpSolver` for events
  and stops. `CpSolver` is generic over one `FnMut(Event) -> ControlFlow<()>`
  callback, because a boxed one keeps the closure's borrows alive until the
  solver drops.
- **Stop.** `StopHandle` stops every solve attached to it, and a stop is sticky,
  like a cancellation token.
- **Model transfer.** Each solve encodes the model once in Rust and parses it
  once in C++. Skipping the copy needs a C++ model that lives across solves.
- **Solution payload.** A zero-copy `CpSolverResponseView`, and
  `to_owned_message` keeps it.
- **Formats.** Buffa's `text` and `json` features. `views` is required, because
  Buffa gates views with the formats.
- **Defaults.** `default_parameters` fills `SatParameters` through C++
  reflection, because Buffa generates no proto2 default getters.

## Modeling API

`CpModel` owns a `CpModelProto` and is its only persistent representation, and
`CpModel::proto_mut` reaches every field the API does not cover.

```text
model.new_var(0..=10) -------------------------> IntVar(i32)
model.new_var(Bool) ---------------------------> BoolVar(i32), !b = -i - 1
model.new_var(Interval::fixed_size(x, 3)) -----> IntervalVar(i32)
x + 2 * y - 3 ---------------------------------> LinearExpr { terms, offset }
(x + 2 * y).le(10).only_enforce_if(b) ---------> Constraint(ConstraintProto)
Constraint::circuit([(0, 1, a)]) --------------> Constraint
model.add(constraint) ---- move into model ----> ConstraintIndex(i32)
```

- **Handles** are typed `i32` indices without a model identity, like `petgraph`
  and `slotmap`.
- **Expressions** sort, merge, and drop zero terms when written, like Python,
  and panic on `i64` overflow, where Python wraps silently or fails.
- **Comparisons** are inherent `eq`, `le`, `in_domain`, and so on, because
  Rust's comparison traits return `bool`. Handles still derive `Ord` by index.
- **Constraints.** Every family is a constructor on `Constraint`, and
  `CpModel::add` is their only insertion path. Variables and intervals come from
  `CpModel::new_var`. The schema stores an interval as a constraint, but
  `new_var` returns an `IntervalVar`, because other constraints reference it by
  index like a variable.
- **Compositions.** Python helpers that compose other calls, such as
  `add_map_domain` and `weighted_sum`, stay compositions, and `docs/parity.md`
  gives each encoding.
- **Responses.** `value` takes any `Evaluate` input and returns `i64`, `bool`,
  or `f64` to match it, on both the owned response and the view.
