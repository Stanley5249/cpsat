# Design

Rust owns the model. Protobuf defines the contract. C++ executes the solver. The FFI exposes only capabilities that Rust cannot implement directly.

The goal is the functional capabilities of the official Python CP-SAT binding, through an idiomatic Rust API that writes into the Protobuf model. `cargo build` acquires OR-Tools and builds the bridge, with no manual OR-Tools, Conda, or Python install, and normal builds regenerate neither Protobuf code nor OR-Tools. A persistent incremental solver, OR-Tools subsystems outside CP-SAT, custom propagation, and a CP-SAT-only fork are out of scope.

## Terms

Names follow the [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/naming.html) and the C convention `prefix_object_verb`.

- **OR-Tools**: the upstream C++ library and its files.
- **bridge**: our C++ code and its C ABI in `crates/cpsat-sys/bridge/`, with functions named `cpsat_<object>_<verb>`, such as `cpsat_model_stats`.
- **Buffa**: the Rust Protobuf library that generates the `proto` types the API exposes.
- **view**: a borrowed, zero-copy reading of an encoded message, such as `CpSolverResponseView`.
- **FFI**: the Rust side of the C ABI, in `cpsat-sys` and `cpsat`'s private `ffi` module.
- **session**: the bridge object that serves one solve and holds its callbacks.
- **mode**: how the build acquires OR-Tools, the `download-libortools` or `build-libortools` feature, or `ORTOOLS_ROOT`.
- **wrapper**: a hand-written type that owns a Protobuf message, such as `CpModel`.
- **handle**: `IntVar`, `BoolVar`, `IntervalVar`, or `ConstraintIndex`.
- **literal**: a `BoolVar`, negated or not.

## Architecture

```text
user code
   |
crates/cpsat          CpModel, Buffa types, CpSolver, StopHandle, diagnostics
   |  (safe Rust, owns the model)
crates/cpsat-sys      build.rs, raw extern "C" declarations, links = "ortools"
   |  (serialized bytes, one fn pointer + context per callback, opaque session)
cpsat-sys/bridge      extern "C" over SolveWrapper and CpSatHelper
   |
ortools.dll / libortools.so  (SolveCpModel)
```

Rust owns the model, serialization, every model change, callback handling, and error interpretation. C++ owns solver execution, the active solve and its stop mechanism, and OR-Tools diagnostics. A bridge session lives for one solve and never holds a second copy of the model.

`crates/cpsat/src` modules depend one way, and every module may use `proto` and `error`:

```text
expr/        handles, LinearExpr, FloatExpr, Domain        uses nothing else
constraint/  Constraint, ConstraintIndex, comparisons      uses expr
solver/      CpSolver, callbacks, stops, responses, ffi    uses expr
model/       CpModel: variables, intervals, lookups        uses expr, constraint,
                                                           solver
proto/       generated by Buffa
```

`solver/` adds `solve`, `validate`, and `stats` to `CpModelProto`, and `CpModel` forwards to them. An inherent method needs no `use`, so this dependency shows only in those calls.

## Facts verified against v9.15

Recheck these when the pinned OR-Tools version changes.

- The prebuilt `ortools` library already contains `SolveWrapper` and `CpSatHelper` from `swig_helper.h`, the native core of Python's solver.
- The C API in `cp_solver_c.h` has no callbacks and aborts on a parse failure, so the bridge wraps `SolveWrapper` instead.
- Solution and best-bound callbacks run under the response mutex, but log and solution callbacks can run on different threads, so the bridge serializes them.
- Python's `ExtSolveWrapper` stores the first callback exception, calls `StopSearch()`, and rethrows after `Solve` returns.
- Both prebuilt archives are dynamic, and `ortools.dll` loads HiGHS and SCIP even for CP-SAT.
- `cp_model.proto` is proto3 and `sat_parameters.proto` is proto2.

## Rules

Every change follows these rules.

- **Protobuf types.** Wrap a message only where its encoding is weakly typed: indices, `-i - 1` literals, flat interval lists, and `oneof` constraints. Use typed records such as `SatParameters` and `CpSolverResponse` as generated, and add methods to them.
- **Wrappers.** A hand-written type is a cheap wrapper over data that OR-Tools or Buffa already lays out. It holds or borrows that data and adds no copy, cache, or translation, as `CpModel` holds only its `CpModelProto` and `Solution` borrows one `repeated int64` row. A type that regroups OR-Tools entry points needs a reason under Decisions.
- **Layers.** Each OR-Tools entry point maps to one bridge function and one Rust method, and its name adapts per layer, as `SolveWrapper::AddLogCallback` becomes `cpsat_session_add_log_callback` and `CpSolver::add_log_callback`.
- **Boundary.** A message crosses the C ABI as serialized bytes. Borrow part of a live C++ message by pointer only when a benchmark shows the copy matters, and name that cost under Decisions.
- **Literals.** The schema refers to a row of `CpModelProto::variables` by its `i32` index. A field named `literal` reads that index as a Boolean on a 0-1 variable, and the negative value `-i - 1` is the negation of row `i`, so a negation adds no row. `IntVar` holds a row index, which is never negative, and `BoolVar` holds a literal, which `!` negates as bitwise not. A literal enters a variable field only through `BoolVar::to_int_var`, which drops the negation, or `LinearExpr::from`, which reads `!b` as `1 - b`. A method that edits a row, such as a domain change, takes `IntVar`. A method that sets a literal's truth value, such as `add_hint`, takes `BoolVar` and flips the value for a negation.
- **Paths.** Every public item has one path. `prelude` holds every hand-written item except `Error` and `Result`, which stay at the root. `proto` holds the generated types and `buffa` re-exports their runtime. Other modules are private.
- **Names.** Use Python's name wherever a Rust convention allows it, such as `constant` and `parameters`. Constructors drop `new_`, constraint constructors drop `add_`, and integer is the unmarked kind. The model and solver take Python's class names, `CpModel` and `CpSolver`. `CpModel::new_var` keeps the prefix, because it appends to the model and a bare `var` reads like a getter. A value before insertion is a plain noun, such as `Constraint` and `Interval`. A handle takes the OR-Tools name where one exists, such as `IntVar` and `IntervalVar`, and is otherwise the noun plus `Index`, such as `ConstraintIndex`, because it is a row index and borrows nothing.
- **Vocabulary.** Each concept has one spelling in identifiers. A type name sets the spelling for every name derived from it: `IntVar` gives `var` and `LinearExpr` gives `expr`, as in `new_var`, `var_mut`, `to_bool_var`, and `exprs`. Prose, doc comments, panic messages, and test names, which read as sentences, spell the full word.
- **Abbreviations.** Identifiers use only these short forms: `var` and `expr` from the type names, `proto` for a Protobuf message, `stats` from OR-Tools, and the `std` forms `min`, `max`, `len`, `rhs`, `eq`, `ne`, `lt`, `le`, `gt`, and `ge`. Every other word is spelled in full, such as `parameters`, `index`, `literal`, and `numerator`.
- **Generated names.** Use Buffa's names as generated, such as `CpModelProto::variables` and `LinearExpressionProto::coeffs`. A binding that destructures such fields takes the field names, as in `let (vars, coeffs, offset)`, and a binding for one element takes the project term, as in `for var in &mut proto.variables`.
- **Paired forms.** When two forms of one concept share a scope, both get the same pattern of names, such as `model` with `model_proto` and `parameters` with `parameters_proto`.
- **Files.** A file takes the spelling of the types it holds. Sibling modules may reuse a file name, as the `expr::linear` and `constraint::linear` modules do.
- **Parity.** Where a Python name breaks a Rust convention or the API's own pattern, the Rust name wins and the Python name becomes a `#[doc(alias)]`.
- **Entry points.** One method per meaning. Several input types share one method over a sealed trait, such as `value` over `Evaluate`, `new_var` over `NewVar`, `add` over `AddConstraint`, and `add_hint` over `Hint`. Take `impl IntoIterator` instead of a single-item twin.
- **Insertion.** `CpModel::new_var` appends a row of `CpModelProto::variables` and `CpModel::add` a row of `CpModelProto::constraints`, so each method maps to one table. Each returns the handle that the input's kind of row calls for: an `IntVar` or `BoolVar` for a variable, an `IntervalVar` for an interval, which other constraints take as input, and a `ConstraintIndex` that only reads any other row. Only these two methods allocate an index and build a handle, through a sealed `FromIndex` trait that code outside the crate cannot call.
- **Methods.** Operations on a model or response are methods on `CpModel`, `CpModelProto`, and `CpSolverResponse`, and `CpModel` forwards `solve`, `validate`, and `stats` to its message. Only `default_parameters` is a free function. Method names do not repeat the receiver.
- **Allocation.** Reads, predicates, and lookups allocate nothing, because callbacks and model-building loops call them often. Building owned model data and encoding each solve are the exceptions.
- **Ownership.** Take stored data by value through `impl Into<T>`, and borrow read-only data, such as `CpSolver::new(&SatParameters)`.
- **Failure.** A caller's programming error, such as `i64` overflow or a ragged table row, panics with a `# Panics` section. A failure the caller can cause in OR-Tools returns `Error`. `validate` returns `Error::InvalidModel`, while `solve` reports the `MODEL_INVALID` status. Types rule out structural mistakes, such as a negated literal where the schema wants a variable or an open range such as `0..` as a variable domain. The validator checks what depends on the model's current state, such as a variable's domain or an earlier hint. Check eagerly only what the validator cannot see. Trust what OR-Tools returns and decode it without checks, so only a caller's mistake, such as a handle from another model, panics while reading a response.
- **Matched lists.** Items that belong together form one tuple, such as the `(interval, demand)` pairs of `cumulative`, so their lists cannot differ in length. Lists whose lengths must match but whose items do not pair, such as the two permutations of `inverse`, stay separate, and the validator reports a mismatch. Only an encoding that hides the mistake panics, such as table rows flattened into one list, which the validator would read as other rows.
- **Lookup.** A raw schema index returns `Option`. Indexing with a handle panics when the model lacks it, like a slice, and indexing with an `IntervalVar` also panics when its row holds no interval.
- **Builders.** A value configured before insertion takes `self` and returns `Self` with `#[must_use]`, such as `Constraint::only_enforce_if`. After insertion, `CpModel::var_mut` edits a variable through setters that keep its fields well formed, and everything else changes through `proto_mut`. `CpModel` holds nothing besides its message, so `proto_mut` cannot leave the model inconsistent. It can only break the handles to rows it changes, such as an `IntervalVar` whose row no longer holds an interval.
- **`#[must_use]`.** Every public method without side effects carries it. Appending model methods such as `new_var` do not.
- **Docs and tests.** `docs/conventions.md` sets the rules for doc comments, examples, and tests.
- **Visibility.** `pub` or private, except `pub(crate)` on handle indices, expression terms and evaluation, and the callback wrappers' `new`, which sibling modules share.

## Decisions

Each decision names the cost it accepts, so a review can weigh it against the rules above instead of taking it as given.

- **Crates.** `cpsat-sys` and `cpsat`, because `links` allows one native link per graph. The two crates release together.
- **Codegen.** `just gen-proto` runs `buf generate` with the remote Buffa plugin, and the output is committed, so normal builds need no `protoc`. `just check-proto` catches committed code that drifts from the protos.
- **Bridge build.** The `cc` crate with definitions read from `ortoolsTargets.cmake`, so the download mode needs no CMake. A new OR-Tools version can change that file's format.
- **Download.** The system `curl` and `tar`, which bring the system proxy and CA store, and fail on a host without them. `build/fetch.rs` says when to switch to `ureq`.
- **Cache.** Archives, extractions, and source builds live in `CPSAT_CACHE_DIR`, each filled once under a `File::lock`, which sets the MSRV.
- **Runtime libraries.** Hard-linked or copied into `OUT_DIR/runtime` with their license notices. A copy across volumes costs about 90 MB per `OUT_DIR`. The `cpsat-sys` build script explains why.
- **Errors.** A `thiserror` enum in `cpsat`, so callers can match on it, and `anyhow` in the build script, whose errors only a person reads.
- **README links.** Absolute URLs on `main` for `docs/`, because crates.io resolves relative links against each crate's directory. The license links stay relative, because each crate holds its own copies. A published crate's docs may then describe unreleased behavior.
- **Solver.** `CpModel::solve` for the plain case, and a `CpSolver` for callbacks and stops. `CpSolver<'a, C>` keeps its callbacks in a nested tuple of `SolutionCallback<F>`, `BestBoundCallback<F>`, and `LogCallback<F>`, because a boxed closure keeps its borrows alive until the solver drops. The cost is that the solver's type names every closure.
- **Stop.** `StopHandle` stops every solve attached to it, and a stop is sticky, like a cancellation token, so a caller replaces a stopped handle instead of resetting it.
- **Model transfer.** Each solve, `validate`, and `stats` call encodes its message once in Rust and parses it once in C++. Skipping the copy needs a C++ model that lives across calls.
- **Solution payload.** The bridge serializes each solution, and the callback reads a zero-copy `CpSolverResponseView`, which `to_owned_message` keeps. This costs about 55 us per solution with 20,000 variables, about 0.5% of the solver's own time, as `benches/callbacks.rs` measures. Borrowing the C++ response would skip it, but needs a hand-written mirror of the response fields.
- **Formats.** Buffa's `text` and `json` features. `views` is required, because Buffa gates views with the formats and solution callbacks read views.
- **Defaults.** `default_parameters` fills `SatParameters` through C++ reflection, because Buffa generates no proto2 default getters. Each call costs one reflection walk, one encode, and one decode.

## Modeling API

`CpModel` owns a `CpModelProto` and is its only persistent representation, and `CpModel::proto_mut` reaches every field the API does not cover.

```text
model.new_var(0..=10) -------------------------> IntVar(i32)
model.new_var(Bool) ---------------------------> BoolVar(i32), !b = -i - 1
x + 2 * y - 3 ---------------------------------> LinearExpr { terms, offset }
(x + 2 * y).le(10).only_enforce_if(b) ---------> Constraint(ConstraintProto)
Constraint::circuit([(0, 1, a)]) --------------> Constraint
model.add(constraint) ---- move into model ----> ConstraintIndex(i32)
model.add(Interval::fixed_size(x, 3)) ---------> IntervalVar(i32)
```

- **Handles** are typed `i32` indices without a model identity, like `petgraph` and `slotmap`.
- **Expressions** sort, merge, and drop zero terms when written, like Python, and panic on `i64` overflow, where Python wraps silently or fails.
- **Comparisons** are inherent `eq`, `le`, `in_domain`, and so on, because Rust's comparison traits return `bool`. Handles still derive `Ord` by their `i32`, so negated literals sort before plain ones.
- **Constraints.** Every family is a constructor on `Constraint`, and `CpModel::add` is their only insertion path. An `Interval` is a constraint row too, so `add` inserts it and returns an `IntervalVar`, and `Constraint::from(interval)` forgets the kind when a plain `ConstraintIndex` suffices.
- **Compositions.** Python helpers that compose other calls, such as `add_map_domain` and `weighted_sum`, stay compositions, and `docs/parity.md` gives each encoding.
- **Responses.** `solution` returns a `Solution` when the status has one, on both the owned response and the view, and `Solution::value` takes any `Evaluate` input and returns an `i64`, `bool`, or `f64` to match it. A `Solution` borrows one `repeated int64` row, so `additional_solutions` reads the same way.
